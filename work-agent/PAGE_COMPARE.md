# Before/after page comparison

Open the PPT project, select the Pages tab in the details panel and choose a page. A page whose current image has at least one earlier image of its own in the current draft shows the "修改前后对比" (Compare before/after) control next to the page title. The comparison replaces the single page picture with the previous image and the current image, labelled 修改前 / 修改后, either side by side or as one overlay with a draggable divider. The selector compares the current image with any of those earlier images. Pages on their first image, pages without a current image and old pages beyond the current page count show no control.

Only the page's own versions are compared. Image history keeps every saved record, including those of an earlier draft that used the same page number for other content. The workflow counts the images a page has had since its draft was last reset or the page was added (image_version), so the view offers that many records at most, ending with the current one. The first image a page gets after a new outline or a material change, or after the page was removed and added again, therefore has nothing to compare, and a sample that never became the page's image is not offered. Saved artifacts carry no draft marker, so this is a count, not an exact boundary: where the count includes an image that is not a record of its own, such as a re-layout page first shown as its original, one record of the previous draft can still be listed.

For a re-layout project the same view compares the original uploaded page with the restyled page, labelled 原稿 / 重排后, and the control reads "原稿对比" (Compare with original). Only the original pages the prepared re-layout lists (relayout.previews) are used. An unchanged page of a deck uploaded again reuses the render saved for the earlier upload and is still that page's original. A page that was not selected for re-layout still shows its original render, so it has nothing to compare. Earlier restyled images of a page stay selectable under the rule above and use the 修改前 / 修改后 labels; restyled images saved before the newest original page of the current source deck belong to an earlier upload and are not offered.

The comparison is strictly view-only. It calls no tool, sends no message and changes neither the current image nor its approval. Switching a page back to an older image is deliberately unsupported: there is no restore, set-current or delete action here or in Image history. To return to an earlier look, describe the wanted change in the conversation so that a new image is generated and reviewed.

One caption line shows the page's latest change request only when the current image is compared with the record immediately before it and the page is ready. The workflow keeps one request text per page, not one per image record, so older records carry no caption, and the text can predate a later regeneration made for another reason such as a template change. Re-layout comparisons show no caption.

The existing workflow artifact registry and signed project asset routes provide the files; images load lazily through the same URL check as Image history. No new database, storage copy, model call or mutation API is involved. withImageHistory in dist/image-history.js additionally marks relayout_source_page artifacts with a UI-only relayout_source label before asset URLs become opaque: is_current when the page still shows that original, in_current_source when the prepared re-layout lists it. These are not numbered image records and compact model snapshots omit the label. Esc closes the view and returns focus to the control; while a dialog is open above the view, Esc closes only the dialog. The divider is one range input, so arrow keys move it. The selector's options carry a data-preview-key each, so the panel's in-place update keeps the shown choice with its record when the list grows. Below 600px the two images stack.

The deployed panel is maintained through the hash-locked transformer tools/page-compare-ui.cjs and its adjacent page-compare-panel.js and page-compare.css. It is the last panel step: its input is pinned by SHA-256 to the dist/ui/index.html that preceded it, it edits two fragments of the slides renderer, appends the panel code and adds one style block. Running it on its own output returns the same bytes; any other document is refused. Regenerate with node tools/page-compare-ui.cjs BASELINE_HTML dist/ui/index.html and never edit the bundle by hand or rebuild the older TypeScript UI over it. A later panel step must pin the output hash this step prints. tests/page-compare.test.mjs covers the labels, the pairing rules, the rendered view, the keyboard handling and the transformer offline with node --test; the agent process must be restarted to serve the new panel and labels.
